## 1. Amazon Bedrock AgentCore Web Search API 공개

- **핵심:** 기존처럼 AgentCore Gateway와 MCP target을 먼저 구성하지 않고도 AWS SDK·CLI에서 IAM 서명으로 web search를 직접 호출할 수 있다.
- **왜 중요한가:** 최신 정보가 필요한 내부 애플리케이션에 검색만 얇게 추가할 때 인프라 복잡도를 줄일 수 있다. 플랫폼 팀이 여러 agent에 공통 정책을 제공하는 경우에는 기존 Gateway 방식이 여전히 적합하다.
- **바로 해볼 것:** 공식 도메인 allowlist, 시간 범위, 지역과 최대 결과 수를 명시하고 검색 결과 URL을 다시 열어 원문 날짜와 내용을 검증한다. query 자체가 내부 의도를 노출할 수 있으므로 검색 로그의 보존·접근 정책도 설정한다.
- **원문:** [AWS — Web Search API on Amazon Bedrock AgentCore](https://aws.amazon.com/blogs/machine-learning/introducing-the-web-search-api-on-amazon-bedrock-agentcore/)

## 2. OpenAI Codex를 Amazon Bedrock 경유로 운영하는 기업 패턴

- **핵심:** Codex는 개발자 workstation에서 실행하면서 지원되는 OpenAI 모델 요청을 Bedrock으로 보내고, AWS IAM·Region·관측성·gateway 정책을 적용할 수 있다.
- **왜 중요한가:** coding agent 도입을 위해 별도의 모델 접근·자격 증명·운영 스택을 만들지 않고 기존 AWS 통제면을 재사용할 수 있다.
- **바로 해볼 것:** 최소 권한 pilot에서 identity와 model path를 먼저 검증한다. provider·credential·Region·OpenTelemetry 설정은 조직 관리 영역에 두고, 저장소 지침은 AGENTS.md에 둔다.
- **주의:** AGENTS.md는 행동 지침이지 보안 경계가 아니다. 강제할 권한·sandbox 요구는 조직 관리 설정과 request path의 gateway에서 시행해야 한다.
- **원문:** [AWS — OpenAI Codex on Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/openai-codex-on-amazon-bedrock/)

## 3. Framework-neutral closed-loop agent 평가: UAEF

- **핵심:** UAEF는 LangGraph·LangChain·Strands·AgentCore 등의 서로 다른 trace를 공통 AgentTrace로 변환하고, 7개 영역의 36개 metric으로 agent 버전을 비교한다.
- **왜 중요한가:** agent framework를 바꿀 때 평가 코드와 과거 기준선을 다시 만드는 결합을 줄인다. tool call, multi-turn, multi-agent coordination, 성능과 responsible AI를 같은 척도로 비교할 수 있다.
- **바로 해볼 것:** 내부 trace schema를 canonical event로 정규화하고 message, tool call, handoff, error, latency, token, cost를 보존한다. expected tool·순서·argument까지 ground truth에 포함한다.
- **보안 포인트:** LLM-as-judge가 평가 대상 출력의 prompt injection에 영향받지 않도록 rubric과 content를 분리하고, evidence span 검증에 실패한 점수는 폐기한다. judge score를 보안 차단 결정으로 사용하지 않는다.
- **원문:** [AWS — Universal Agent Evaluation Framework](https://aws.amazon.com/blogs/machine-learning/uaef-a-framework-agnostic-system-for-closed-loop-evaluation-of-ai-agents/)

## 4. 분산 학습의 silent data corruption 탐지·복구

- **핵심:** GPU가 오류를 보고하지 않은 채 그럴듯하지만 잘못된 값을 반환하는 SDC를 잡기 위해 non-finite gradient check, ring replay audit, weight fingerprint 비교를 학습 루프에 추가한다.
- **왜 중요한가:** loss가 정상처럼 보이는 동안 잘못된 값이 모든 replica의 gradient와 weight로 확산될 수 있으며, 장시간 대규모 학습 비용을 통째로 잃을 수 있다.
- **바로 해볼 것:** 정기 audit step에서 다른 node의 micro-batch를 재계산하고 loss bit equality와 gradient fingerprint를 비교한다. 이상 rank를 node에 매핑해 격리하고 마지막 검증 checkpoint에서 재시작한다.
- **원문:** [AWS — Detecting silent data corruption on SageMaker HyperPod](https://aws.amazon.com/blogs/machine-learning/detecting-and-recovering-from-silent-data-corruption-on-amazon-sagemaker-hyperpod/)

## 5. Mission-critical agent를 위한 multi-model substrate와 harness 분리

- **핵심:** DXC OASIS는 Bedrock을 다중 모델에 대한 governed substrate로 사용하고, 그 위에 자체 orchestration·governance·assurance harness를 둔다.
- **왜 중요한가:** model gateway가 제공하는 identity·network·data boundary와 업무별 agent가 제공해야 하는 최소 권한·승인·검증을 분리하면 model 교체와 정책 일관성을 동시에 확보하기 쉽다.
- **바로 해볼 것:** model substrate와 agent harness의 책임을 표로 나눈다. 모델 라우팅·credential·network·logging은 공통 계층에, 업무 권한·승인·tool policy·task verification은 harness에 둔다.
- **판단:** 공개된 평균 resolution-time 95% 감소는 56개 내부 use case 결과이므로 자체 incident 유형과 human review 비용을 포함해 재측정해야 한다.
- **원문:** [AWS — DXC multi-model AI substrate](https://aws.amazon.com/blogs/machine-learning/how-dxc-technology-built-a-multi-model-ai-substrate-on-amazon-bedrock/)

## 6. MCP tool schema와 Agent Registry의 push 동기화

- **핵심:** MCP server에 tool이 추가되거나 schema가 변경될 때 registry metadata를 자동 갱신하는 push-based 패턴이 공개됐다.
- **왜 중요한가:** registry가 오래된 schema를 제공하면 consumer agent가 잘못된 argument나 제거된 tool에 의존하고, catalog 신뢰도가 급격히 떨어진다.
- **바로 해볼 것:** 배포 pipeline이 MCP schema digest와 semantic version을 생성하고, 호환성 검사 후 registry를 갱신하도록 한다. breaking change는 이전 버전을 유지한 채 새 endpoint/version으로 게시한다.
- **원문:** [AWS — Automating Agent Registry updates](https://aws.amazon.com/blogs/machine-learning/automating-aws-agent-registry-updates-with-push-based-architecture/)

## 7. Lakehouse에서 MCP까지: agent용 data foundation

- **핵심:** agentic AI의 데이터 기반을 통합 lakehouse, structured/unstructured data governance, 공통 semantic layer, MCP interface로 연결하는 참조 방향이 제시됐다.
- **왜 중요한가:** retrieval 품질 문제는 모델보다 분산된 데이터, 불일치한 business meaning, 문서 권한과 freshness에서 시작하는 경우가 많다.
- **바로 해볼 것:** raw source와 agent tool 사이에 데이터 소유자, freshness SLO, lineage, row/document-level access, semantic definition을 명시한다. MCP server는 데이터 권한을 재구현하지 말고 기존 정책을 상속해야 한다.
- **원문:** [AWS — Data foundation for agentic AI: lakehouse to MCP](https://aws.amazon.com/blogs/big-data/build-a-data-foundation-for-agentic-ai-on-aws-from-lakehouse-to-mcp/)
