## 1. OpenAI의 persistent agent 보안 운영 패턴

- **핵심:** OpenAI는 24시간 자율 실행되는 agent를 위해 신뢰된 control plane, Codex sandbox, auto-review, agent 전용 identity와 전면 logging을 결합한다고 설명했다.
- **왜 중요한가:** persistent agent는 설정과 코드를 스스로 변경하고 사용자 입력 없이 행동하므로, 전통적인 정적 애플리케이션보다 권한 누적·지침 변질·review fatigue 위험이 크다.
- **바로 해볼 것:** control plane 변경과 agent turn을 모두 감사 로그에 기록하고, 사용자 identity와 agent identity를 분리한다. 경계를 넘는 행동은 보조 review model이 먼저 선별하고 고위험 사례만 사람에게 올린다.
- **주의:** model reviewer는 결정론적 sandbox·권한 정책을 대체하지 않는다. OpenAI 내부 사례에서도 auto-review와 정적 제어를 겹쳐 사용한다.
- **원문:** [OpenAI — Securing persistent agents](https://developers.openai.com/blog/securing-persistent-agents-like-openclaw-at-openai)

## 2. 자동 공격자를 확장해 fuzzy robustness 훈련

- **핵심:** OpenAI는 공격 모델의 test-time compute를 늘려 반복적으로 jailbreak를 탐색하고, 여러 실행에서 성공하는 worst@n 공격을 adversarial training 데이터로 사용했다.
- **왜 중요한가:** cyber·biology처럼 허용/금지 경계가 맥락에 따라 달라지는 dual-use 영역에서는 고정 jailbreak 세트만으로 적응형 다중 턴 공격을 대표하기 어렵다.
- **바로 해볼 것:** red-team harness가 defender 응답을 보고 공격 프롬프트를 반복 수정하도록 만들고, 단일 성공이 아니라 여러 seed·재실행에서 재현되는 공격만 학습·회귀 데이터에 넣는다.
- **평가:** 안전성 상승과 benign refusal 증가를 함께 측정해 safety-helpfulness Pareto를 확인한다. 모델층 개선과 production safeguard는 별도 계층으로 유지한다.
- **원문:** [OpenAI Alignment — Improving Fuzzy Robustness](https://alignment.openai.com/fuzzy-robustness/)

## 3. 차세대 AgentCore runtime: compute와 workspace를 같은 trust boundary로

- **핵심:** AgentCore는 session별 hardware-isolated 환경, 별도 identity·policy·audit trail에 더해 S3-backed filesystem을 동적으로 mount·저장할 수 있게 했다.
- **왜 중요한가:** compute만 격리하고 작업 파일·artifact·memory가 외부 공유 경로에 남으면 workspace leakage와 privilege escalation 위험이 지속된다.
- **바로 해볼 것:** session별 filesystem prefix와 임시 credential을 발급하고 종료 시 폐기한다. 지속해야 하는 artifact는 명시적 allowlist 경로만 저장하며, 다음 실행에서 자동 신뢰하지 말고 provenance와 signature를 검증한다.
- **원문:** [AWS — Next-generation AgentCore runtime](https://aws.amazon.com/blogs/machine-learning/run-agents-securely-and-efficiently-with-the-next-generation-agentcore-runtime/)

## 4. Managed Knowledge Base tool의 세밀한 접근 제어

- **핵심:** agent가 사용자를 대신해 반복 검색하더라도 사용자가 볼 수 있는 문서만 retrieval하도록 policy와 interceptor를 적용하는 패턴이 공개됐다.
- **왜 중요한가:** RAG agent가 스스로 query를 재작성하면 애플리케이션 UI의 필터만으로는 권한을 보장할 수 없다. retrieval 계층에서 user·agent·resource 권한을 매 호출마다 강제해야 한다.
- **바로 해볼 것:** document metadata에 tenant·department·classification을 넣고, 인증된 사용자 claim에서 server-side filter를 생성한다. 모델이 filter를 제공하거나 변경하지 못하게 하고 denied retrieval도 감사한다.
- **원문:** [AWS — Fine-grained access control for Managed Knowledge Base tools](https://aws.amazon.com/blogs/machine-learning/fine-grained-access-control-for-amazon-bedrock-managed-knowledge-base-tools/)

## 5. A2A 기반 조직 간 multi-agent 상호운용

- **핵심:** 서로 다른 조직과 framework의 agent가 내부 구현을 노출하지 않고 discovery, task 교환, 진행 상태와 결과를 주고받는 A2A 패턴이 제시됐다.
- **왜 중요한가:** agent integration을 고객·framework마다 별도 구현하면 인증·상태·오류 처리와 계약 관리가 중복된다.
- **바로 해볼 것:** agent card에 capability, input/output schema, auth, data classification, timeout과 idempotency를 명시한다. 외부 agent의 응답과 artifact는 신뢰하지 않는 입력으로 검사하고 delegation depth와 비용 상한을 둔다.
- **원문:** [AWS — Composable multi-agent systems with A2A](https://aws.amazon.com/blogs/machine-learning/build-composable-interoperable-multi-agent-systems-with-a2a-on-aws/)

## 6. Bedrock·LiteLLM 기반 self-service LLM gateway

- **핵심:** LiteLLM을 Fargate에 배포하고 Bedrock Application Inference Profiles를 OpenAI-compatible API 뒤에 숨겨 모델 접근을 중앙 관리하는 패턴이 공개됐다.
- **왜 중요한가:** 개발자는 coding assistant를 쉽게 연결하면서 플랫폼 팀은 latency·error·사용량·비용 귀속과 access control을 한 지점에서 적용할 수 있다.
- **바로 해볼 것:** team/project별 virtual key, quota, model allowlist와 budget을 적용한다. gateway 장애가 전체 개발 흐름을 멈추지 않도록 다중 AZ, health check, circuit breaker와 제한된 direct-access 비상 경로를 설계한다.
- **원문:** [AWS — Self-service LLM gateway with Bedrock and LiteLLM](https://aws.amazon.com/blogs/machine-learning/building-a-self-service-llm-gateway-with-amazon-bedrock-and-litellm/)

## 7. Agent DLC: agent 변경을 CI/CD evidence로 검증

- **핵심:** agent를 containerized development lifecycle에 넣고 반복 가능한 평가와 배포 증거로 prototype-to-production 전환을 판단하는 패턴이 소개됐다.
- **왜 중요한가:** agent는 동일 입력에도 경로가 달라질 수 있어 전통 unit test만으로 readiness를 판단하기 어렵다. 모델·prompt·tool 변경마다 behavior regression을 재현할 수 있어야 한다.
- **바로 해볼 것:** image에 agent code와 dependency를 고정하고 평가 dataset·model ID·seed·tool mock 버전을 함께 기록한다. CI에서 task success, policy violation, trajectory length, token cost와 p95 latency를 비교해 gate를 건다.
- **원문:** [AWS — Engineering agents with Agent DLC](https://aws.amazon.com/blogs/machine-learning/from-prototype-to-production-engineering-agents-with-agent-dlc/)
